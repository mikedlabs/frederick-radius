# Frederick Radius — Engineering Review

**Reviewed:** 2026-05-30 · whole-app read (76k LOC, 261 components, 41 integrations, 59 unit specs).
**Lens:** velocity + tooling · architecture + performance · product + connectedness · code quality + design system · modern Next 16 / React 19.
**How to read it:** findings are ranked by leverage, not by area. P0 is "do this week, it unblocks everything else." Every item has the evidence, the real fix, and the tool. Companion to `AUDIT.md` (state) and `ROADMAP.md` (sequencing). This review disagrees with the current phase order in one place and says so.

---

## The thesis

This is a strong codebase built by someone who knows what they are doing. React Compiler, View Transitions, Skew Protection, Turbopack, ISR with tagged cache invalidation, a disciplined single-source closed-business predicate, 59 unit specs, full next/image adoption. The gaps are not sloppiness. They are two specific structural tensions that everything else hangs off:

1. **The catalog is a 12 MB static JSON parsed at module load, and the Postgres + PostGIS database that should hold it is fully modeled but unpopulated.** You are paying the cost of having a database (schema, migrations, Drizzle, connection pooling) and getting almost none of the benefit. Three of your named pain points (cold first byte, the 2 MB client bundle, no real spatial query) are the same problem wearing three coats.

2. **Coordination and quality are enforced by honor system, not by machine.** Two AI agents hand off through a hand-edited `AGENTS.md`, and the only thing CI checks on a pull request is editorial style. There is no typecheck, test, or build gate. For a one-maintainer shop running two agents in parallel, this is the single cheapest place to buy speed and safety.

Fix those two and the rest is polish. The polish list is real and included, but do not let it jump the queue.

## What is already excellent (so the criticism calibrates)

- **Modern runtime is genuinely modern.** `reactCompiler: true`, `experimental.viewTransition`, Turbopack root, Skew Protection via `deploymentId`, Sentry wrapped for runtime-only capture. Most teams running Next 16 are not using this much of it.
- **The cache design in `now-picks.ts` is correct.** Ten-minute bucket keys, deployment-hash in the cache key so a build busts stale Blob URLs, `revalidateTag("now-picks","max")` for stale-while-revalidate. That is senior work.
- **The data-cleaning pipeline is disciplined.** `publicPlaces()` as the one canonical set, dedup + autoFold + human overrides composed in a documented order, every mutation gated by an env flag for instant rollback. The closed-business predicate is enforced in one place.
- **next/image is fully adopted.** Zero raw `<img>` in the component tree. `AUDIT.md` still lists "some `<img>` tags" as a perf issue. That line is stale. Close it.
- **The data-refresh GitHub Action is clever.** Force-pushing snapshots to an orphan branch keeps main small, and it opens an issue plus dispatches a diagnosis on failure. Keep that pattern.

You do not need reassurance, so that is the last of it. The rest is what to sharpen.

## P0 — Do this week. Highest leverage, lowest risk.

### P0.1 Add a real CI gate (velocity + quality)

**Evidence:** `.github/workflows/` runs `data-refresh`, `freshness-check`, and `style` (editorial lint). Nothing runs `tsc --noEmit`, `vitest`, `eslint`, or `next build` on a pull request. You have 59 specs and a typed codebase and none of it is mechanically enforced. `AGENTS.md` asks agents to "run `npx tsc --noEmit` minimum" by hand.

**Why it is P0:** you are coordinating two autonomous agents. The handoff rule "tests must pass before committing" is unenforceable by a markdown file. A green check is enforceable. This is the change that lets you trust agent output without reading every diff.

**Fix (shipping it in this session):** a `ci.yml` that runs typecheck, lint, unit tests, and a build on every PR and push to main. Node pinned to match local.

**Tool:** GitHub Actions matrix, `npm ci`, the scripts you already have. Add `.nvmrc` so CI and local agree (your `style.yml` comment admits the Node 20 vs 25 drift, that is why it uses `npm install` instead of `npm ci`, fix the root cause).

### P0.2 Delete the dead weight (architecture + bundle)

**Evidence, all confirmed repo-wide:**

| Dead thing | Proof | Action |
|---|---|---|
| `maplibre-gl` dependency | 0 imports in source (only in `package.json` and `.next` cache) | remove from `package.json` |
| `src/components/ui/Sheet.tsx` | 0 importers; its own header calls it "the canonical bottom sheet" but Vaul's `BottomDrawer` won (4 importers) | delete |
| `src/components/ui/TapButton.tsx` | 0 importers | delete |

**Why it matters beyond tidiness:** `api-client.ts` is a zombie data layer with its own `Place`, `Event`, `SearchResult` types that shadow the real ones. An agent searching for "how do I fetch places" can land on it and wire new code to a dead localhost endpoint that silently returns demo fallbacks. Dead code that looks load-bearing is worse than no code.

I am removing the four zero-risk items in this session (`maplibre-gl`, `Sheet.tsx`, `TapButton.tsx`, `api-client.ts` + `live-data-engine.ts`) and verifying with a typecheck.

### P0.3 Get the demo data out of the production map (product + trust)

**Evidence:** the live `src/components/map/AppMap.tsx` and `src/components/map/popups.tsx` import `food-trucks-demo` and `radius-points-demo`, and the map pulls from `city-data-engine`. Your entire positioning is "the honest field guide, no fabricated data." Shipping `food-trucks-demo.ts` on the real `/map` undercuts the one thing that differentiates you.

**Fix:** decide per layer. If food trucks are a real layer, wire them to a real source (you already have the integrations pattern). If not, gate the demo layers behind a `?demo=1` flag or move them to the marketing route only. This is a half-day and it protects the brand promise.

**This is a dot worth connecting:** `city-data-engine.ts` (20 KB) and `frederick-data.ts` are shared by both the marketing microsite and the live app. The marketing scenes are allowed to use stylized data. The app is not. Split the import so the app can never accidentally render a marketing demo number.

## P1 — This month. The structural unlock.

### P1.1 Make Postgres the source of truth for places and events

**Evidence:** `src/lib/db/schema.ts` defines `places`, `events`, `follows`, `place_claims`, `push_subscriptions`, `submissions`, and more, with indexes. The schema comment is honest: "the runtime source of truth for the place catalog is still the merged JSON ... the existing `places` table is a future-prep mirror that isn't populated at write time." Meanwhile `getPlaceBySlug`, `rankPlaces`, `placesWithinRadius`, and `nearby_places` all run JS `haversineMeters` loops over all ~1,725 places, and the only spatial index defined is `places_lng_lat_idx`, a btree on `(lng, lat)`, which a radius query cannot use.

**Why this is the keystone:** populating the DB from the same pipeline that builds the JSON collapses three separate problems into one fix:

- **Cold first byte (your own "known perf issue").** `/today`'s `RightNowStrip` ranks the full set at request time. With the catalog in Postgres and a `geography(Point,4326)` column plus a GIST index, "open places near downtown, rated 4.0+, in these categories" is an indexed query returning 80 rows, not a 1,725-row decorate-and-sort in Node.
- **The 2 MB client bundle.** `places-client.json` exists only because importing the server loader dragged the 12 MB enrichment into the browser. With a real backend, the client calls `/api/nearby` and `/api/search` and ships zero catalog JSON. The stale build-time `open_status` problem (documented in `places-client.ts`) disappears because the server computes it live.
- **The follow / claim / submission features.** Those tables are already DB-native. Right now your catalog and your user data live in two different worlds (JSON vs Postgres) and cannot join. Put them in one place and "show me updates from places I follow" is a join, not a cross-reference.

**Fix, sequenced so it is reversible:**

1. Write a `build:db` script that loads the same `publicPlaces()` output into the `places` table. You already have `toPlace()` / `toEvent()` converters in `db/queries.ts`, so the read path is half-built.
2. Add the spatial column and index in a migration. Your `POSTGIS_NOTE` only adds trigram and FTS indexes. It is missing the geography GIST index, which is the whole point. Add it.
3. Move `placesWithinRadius` and `nearby_places` to SQL `ST_DWithin` behind the existing `dbAvailable()` flag, JSON as the fallback. Ship dual-path, measure, then retire the JSON read.

**Tool:** Drizzle (installed), PostGIS on Supabase (one `CREATE EXTENSION postgis`), `ST_DWithin` / `ST_Distance`. This is the migration the schema was clearly built for. Do it before more feeds, not after.

### P1.2 Move place ranking onto Cache Components (`use cache`)

**Evidence:** `now-picks.ts` says it plainly: "Uses `unstable_cache` ... alongside the Cache Components migration that will land in a follow-up PR." The origin is currently `void`ed inside the cached functions, so personalization is silently disabled (every user gets Frederick-center picks). The ranking still decorates the full set inside the cache fill.

**Fix:** once P1.1 lands, the cached function ranks a small SQL result, not the world. Migrate these surfaces to Next 16 Cache Components (`use cache` with `cacheTag` / `cacheLife`) so caching is a first-class boundary rather than a wrapper, and so you can layer Partial Prerendering on `/today` (static shell streams instantly, the three live picks stream in). That directly kills the 600 to 800 ms cold first byte you flagged.

**Tool:** `use cache`, `cacheLife`, `cacheTag`, PPR, and `<Suspense>` boundaries around `RightNowStrip`.

### P1.3 Turn on `noUncheckedIndexedAccess`

**Evidence:** `tsconfig.json` has `strict: true` but not `noUncheckedIndexedAccess`, and the entire data layer is `Record<slug, X>` indexing: `BASE_BY_SLUG[slug]`, `ENRICHMENT[p.slug]`, `MUNICIPALITY_BY_SLUG["urbana"]`. This is the exact bug class the flag exists for: a missing slug returns `undefined` at runtime while the types claim it cannot.

**Fix:** turn it on, fix the surfaced errors (most become a `?.` or an explicit guard you actually want). Do it as its own PR so the diff is reviewable. Also bump `target` from `ES2017` to `ES2022`; React 19 and Next 16 already emit modern output, ES2017 only makes your own transpiled helpers larger.

**Tool:** TypeScript. This is a one-time tax that pays out on every future slug lookup an agent writes.

## P2 — This quarter. Polish and connectedness.

### P2.1 Adopt the canonical Button instead of designing a new one

**Evidence:** `Button.tsx` has 4 importers, `animated-button.tsx` has 2, `TapButton.tsx` has 0. Across 261 components that means almost every button is an ad-hoc inline `<button className=...>`. `ROADMAP.md` lists "canonical `<Button>` component" as not-yet-built, but the component exists. The problem is adoption, not design.

**Fix:** pick `Button.tsx` as canonical, fold `animated-button` into it as a `motion` prop, delete `TapButton` (doing this now, it is dead), then add an ESLint rule that flags raw `<button>` outside `ui/`. Mechanical adoption beats a style guide nobody runs.

### P2.2 Collapse PlaceCard's four variants with a density prop, but verify the need

**Evidence:** `PlaceCard.tsx` carries `variant: "row" | "feature" | "tile" | "grid"` in one 500-line file. This is less bad than `AUDIT.md`'s "card variant sprawl" implies, it is already one component. The real smell is the breadth of card-ish components in `components/place/` (PlaceCard, PlaceList, PlaceHero, PlaceSheet, KnownForCard). Before refactoring, screenshot all four variants side by side. If two are visually 90% identical, merge those two. Do not abstract four genuinely different layouts into one prop-driven monster, that trades duplication for complexity.

### P2.3 Surface the orphaned editorial routes

**Evidence:** `/parks`, `/trails`, `/transit`, `/rivers`, `/history` are all marked half-working in `AUDIT.md` with the note "not surfaced from /today or /browse strongly enough." The data and the pages exist. The connection does not.

**Fix:** this is your Phase 4, and it is mostly link plumbing plus one good "Field Guide" entry surface on `/today`. The map already has the layer data. Cross-link event to nearby parking to nearby coffee, which the schema and loaders already support (`nearby_places`, `eventsAtVenue`). High product return for low engineering cost.

### P2.4 Fill the Plan tab's feeds (this is a velocity problem disguised as a product problem)

**Evidence:** `/events` is the one core tab marked half-working, because Weinberg, Delaplaine, Ticketmaster, and Bandsintown are all scaffolded-but-inert. Three of those need an env var or a five-minute outreach email, not engineering (`ROADMAP.md` says so).

**Fix:** this is not code. Request the Ticketmaster dev key today, email Weinberg and Delaplaine for an iCal URL, and the Plan tab goes from thin to real. The engineering is already done and waiting behind a missing string. Treat the inert-integration list as a checklist, not a backlog.

## Connect the dots: three things the phase plan misses

1. **Your CI gap and your two-agent workflow are the same problem.** The roadmap treats "snappiness" and "trust" as the next phases, but the thing actually slowing you down is that every agent handoff is unverified. Ship P0.1 and the agents can move faster because their output is checked by a machine, not by you reading diffs. Velocity work comes before polish work.

2. **The database is not a "someday migration," it is the prerequisite for three roadmap items at once.** "RSC streaming for /now," "real-time event status," and the whole follow/claim/business-update system in your schema all assume a live backend. You built the schema for it. Populating it (P1.1) is the unlock, and it is being deferred behind polish.

3. **Demo data in the live map quietly contradicts the pitch.** `/trust` promises honest sources. `AppMap` imports `food-trucks-demo`. A user who clicks a fake food truck pin and finds nothing there learns not to trust the map, which is the product. This is small to fix and disproportionate in damage.

## The modern Next 16 / React 19 toolkit you asked about

You are already using more of it than most. Here is what is left, ranked by payoff for this app specifically:

| Feature | Use it for | Payoff |
|---|---|---|
| **Cache Components (`use cache`)** | the `now-picks` ranking, place + event detail | first-class caching boundary, replaces `unstable_cache`, you already planned it |
| **Partial Prerendering (PPR)** | `/today`, `/places/[slug]` | static shell paints instantly, live picks stream in, kills cold first byte |
| **`next/after`** | `feed-snapshot` writes, analytics, the page-visit tracker | move non-critical work off the response path |
| **`<Suspense>` streaming** | `RightNowStrip`, `FeaturedTonight`, weather | the page does not block on the slowest data source |
| **`experimental.optimizePackageImports`** | `lucide-react`, `framer-motion`, `@vercel/*` | tree-shake large icon/animation libs, smaller client chunks |
| **Route-level `runtime`/`preferredRegion`** | API routes near Supabase | shave latency on DB-backed routes once P1.1 lands |

Two you can turn on essentially for free: `optimizePackageImports` for `lucide-react` (you import icons everywhere) and `next/after` for the feed-snapshot writes (they are pure telemetry and should never be on the critical path).

## Revised sequencing (vs the current five-phase plan)

The current order is Audit, Trust, Premium cards, Connectedness, Snappiness. I would reorder around leverage:

1. **Week 1 — Mechanical safety.** CI gate, `.nvmrc`, delete dead code, demo data out of the live map. (P0)
2. **Weeks 2 to 4 — The database unlock.** Populate Postgres, add the PostGIS GIST index, dual-path the spatial queries. This is your real "snappiness" phase and it is the prerequisite for half of the rest. (P1.1)
3. **Weeks 4 to 5 — Cache Components + PPR on `/today`.** Now that ranking is an indexed query, make caching first-class and stream the shell. (P1.2)
4. **Parallel, non-engineering — Feeds.** Get the keys and the iCal URLs while the DB work happens. (P2.4)
5. **Then polish.** `noUncheckedIndexedAccess`, Button adoption, card audit, editorial cross-linking. (P1.3, P2.1 to P2.3)

Trust and premium-cards are real, but they are the reward for fixing the engine, not the engine.
