  thirteen typo-class corrections, including five where the stored address
  was already right and only the blurb carried the mash.

  pattern catches a narrow class of error; address drift is wider.

### Implications

1. **A second cleanup pass is warranted.** Even the conservative 10 % is
   double the threshold. The blurb-mash pattern only catches records whose
   *blurb* carries multiple addresses; addresses that drifted silently (no
   mash signal) won't surface this way.

2. **Text Search alone is not ground truth.** The four "search artifact"
   rows show that for B2B / one-person-shop records with no strong Google
   listing, the biased Text Search will happily return a similar-named
   neighbor. The follow-up pass needs a stricter accept criterion (exact
   name match required, or human review) before trusting Google's reply.

3. **The DFP set still carries placeholder UUIDs in `google_place_id`.**
   Only one of the 17 had a real `ChIJ…` ID (and that one 404'd). The whole
   set would benefit from a re-resolution pass that backfills real Google
   IDs where the name + address can be matched confidently — then future
   audits become a cheap Place Details call instead of fuzzy Text Search.

### Recommended next steps (not in this PR)

- Spot-check the four candidate-relocation rows above and apply the same
  treatment as Group B (update address + geom + `is_verified: false`).
- Fix `cranberryjade-services-middletown-md`'s address (just `"Frederick"`
  is meaningless) or drop the row.

  `East St` (Frederick has both spellings for the same street).
- Add a periodic `audit-dfp-sample.ts` cron at a larger sample size (200?)
  with a strict accept rule (name match required), and surface the disagree

  rows, some by Place Details, most by Text Search) — well within normal
